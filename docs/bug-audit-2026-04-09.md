## 3. 主要ユーザーシナリオ実行時の検証結果

以下のシナリオを読解ベースで検証（コード上の流れを追跡）

### シナリオ1: 新規登録→プロフ→検索→いいね
✓ **バックエンド:** 処理は正常（Registration API → UserProfile自動作成 → Profile取得 → Like作成 → Match生成）
✓ **フロント:** API呼び出しは適切（状態管理は基本的）
⚠ **問題候補:** いいね後の画面更新（マッチ判定の遅延再取得）

### シナリオ2: マッチ→チャット→メッセージ送信
✓ **バックエンド:** メッセージ作成・制限チェック・通知トリガー正常
⚠ **フロント:** ChatRoom でメッセージ受信を定期poll（4秒間隔）→ 遅延可能性
⚠ **制限チェック:** フリープランユーザーの1通制限はAPI側で実装だが、フロント側では制限表示がない可能性

### シナリオ3: プロフ画像アップロード→一覧反映
⚠ **バックエンド:** 画像保存 → ProfilePhoto.sync_main_to_profile() で UserProfile.profile_image に同期
⚠ **フロント:** uploadPhoto() → await loadPhotos() で再取得 → OK ですが、同期の遅延リスク
❌ **問題:** デリゲート参照（profile_image vs ProfilePhoto）の不整合リスク

### シナリオ4: 本人確認アップロード
✓ **バックエンド:** VerificationSubmission作成、DB保存正常
⚠ **フロント:** アップロード後に listVerifications() で再取得 → 表示更新OK
⚠ **問題:** 承認ステータスがwebhook待ち（外部依存）、フロント側では定期同期なし

### シナリオ5: Stripe課金→プランステータス反映
⚠ **バックエンド:** `/api/payments/checkout/` で session作成のみ → webhook処理は別途実装必須
⚠ **フロント:** PlanSuccess画面で session_id 取得後、ステータスを見に行く処理が不明
❌ **問題:** 課金成功後のプロフィール反映メカニズムが不完全

## 4. 発見した不具合一覧

### [確認できた不具合] 優先度 HIGH以上

#### BUG-001: メッセージ制限表示の欠落
**症状:** フリープランユーザーが最初のメッセージを送った後、2通目を送ろうとしてもUI上に「1通限定」という警告が表示されない
**発生条件:** can_send_message_to() が False を返す場合
**再現手順:**
1. フリープランユーザーAが、フリープランユーザーBに初回メッセージを送信
2. Aが再度Bへのチャット画面を開く
3. 送信ボタンが有効（disabled状態でない）
4. 2通目送信を試みる → 403エラー → "送信に失敗しました"と表示のみ

**原因候補:**
- `/frontend/src/views/ChatRoom.vue` で `can_send_message_to()` チェックが存在しない
- API側 `MessagesAPI.post()` で403を返すが、フロント側で detail_code='FIRST_MESSAGE_ONLY' をハンドルしていない
  - `/frontend/src/api.js` line 68-69 で detail_code をチェックするも、ChatRoom では catch で括られている

**ファイル:**
- `/core/models.py` L161-173: `can_send_message_to()` ロジック
- `/core/api_views.py` L320-330: メッセージ送信制限ロジック
- `/frontend/src/views/ChatRoom.vue` L78-87: 送信ハンドラー、エラー表示

**修正方針:** ChatRoom でメッセージ送信前に can_send_message_to() チェックを実装、または詳細なエラーメッセージを表示

#### BUG-002: プロフィール画像同期の遅延・重複リスク
**症状:** ProfilePhoto テーブルと UserProfile.profile_image フィールドの二重管理により、キャッシュ不整合やN+1クエリが発生
**発生条件:** 複数デバイス同時操作、または画像削除直後の検索操作
**再現手順:**
1. デバイスAでプロフィール画像を更新（ProfilePhoto作成 → sync_main_to_profile）
2. 同時にデバイスBで自分のプロフィール取得 `/api/me/`
3. ProfileSerializer が profile_image_url を構築（ProfilePhoto優先、なければ profile_image フォールバック）
4. デバイス間で画像URL異なる可能性

**原因候補:**
- `/core/api_serializers.py` L73-81: get_profile_image_url が ProfilePhoto→profile_image の2段階フォールバック
- `/core/models.py` L244-256: sync_main_to_profile() は save() で永続化だが、キャッシュ不整合時にズレる可能性
- `/core/api_views.py` L700: アップロード後 sync_main_to_profile() → 同期タイミングの遅延

**ファイル:**
- `/core/models.py` L244-256: ProfilePhoto.sync_main_to_profile()
- `/core/api_serializers.py` L73-81: get_profile_image_url()
- `/frontend/src/views/ProfileEdit.vue` L175-179: onCropConfirm で loadPhotos() → API呼び出しで最新取得

**影響範囲:** 画像が表示されない、または古い画像が表示される、検索結果に反映されない

**修正方針:** UserProfile.profile_image フィールドを廃止、ProfilePhoto のみを正本にする（マイグレーション必須）

#### BUG-003: いいね後のマッチ判定が常に再取得
**症状:** UserProfileDetail でいいね後、マッチ状態を確認するために全マッチ一覧ページを複数回取得（最大5ページ）→ 遅い・無駄

**再現手順:**
1. プロフィール詳細ページでいいねボタンクリック
2. likeUser() API呼び出し → res.matched チェック
3. matched=true なら直接チャット画面へ
4. matched=false の場合、フロント側で isLiked.value = true （即座に反映）
5. しかし初回ロード時は checkMatched() が fetchMatches(1~5) で全5ページ分取得

**原因候補:**
- `/frontend/src/views/UserProfileDetail.vue` L34-43: checkMatched() が5ページまで全取得する設計
- `/frontend/src/api.js` line 84 で likeUser() の返り値に matched フラグがあるが、初回チェックに使わない場合がある

**ファイル:**
- `/frontend/src/views/UserProfileDetail.vue` L34-43: checkMatched()
- `/frontend/src/views/UserProfileDetail.vue` L62-65: 初回ロード時に Promise.all で 3つの確認を並列実行

**修正方針:** likeUser() の返り値 matched を活用して、UI上のマッチ状態を即座に更新。初回加算の 5ページ取得を制限（or 1ページのみ）

## 10. すぐ直すべき TOP 5

### **[1] Stripe webhook 実装（SUSP-002）**
**理由:** 決済機能が完全に破壊。ユーザーがお金を払ってもプランが有効にならない。
**アクション:**
- `payments/views.py` 作成 → webhook エンドポイント
- Stripe webhook key 設定
- Payment → UserProfile.plan/plan_expiry 同期ロジック
- webhook rerun テスト

---

### **[2] メッセージ送信制限の UI フィードバック（BUG-001）**
**理由:** UX の大幅な低下。ユーザーが「なぜ送信できないのか」わからない。
**アクション:**
- ChatRoom で API エラー detail_code をパース
- FIRST_MESSAGE_ONLY → "初回メッセージのみ送信できます。スタンダードプランに加入してください"
- ボタンを disabled に（事前チェック optional）

---

### **[3] ProfilePhoto 正本化（BUG-002）**
**理由:** 複数のメディア参照先で不整合 → 画像が表示されない、古い画像が表示される。
**アクション:**
- マイグレーション: profile_image → ProfilePhoto に一括移行
- UserProfile.profile_image を削除 or deprecated
- Serializer で ProfilePhoto のみを参照

---

### **[4] いいね後のマッチ判定最適化（BUG-003）**
**理由:** UX が遅い（5ページ取得待ち）。
**アクション:**
- likeUser() の返り値 matched をそのまま UI に反映
- checkMatched/checkLiked の 5ページ取得を廃止（or 1ページのみ）

---

### **[5] Report unique_together 修正（L-005）**
**理由:** 通報機能が想定通り機能しない（重複防止が効かない）。
**アクション:**
- constraint に DateTrunc('day') を適用
- または created_date フィールド追加 + constraint 修正
- テスト: 同一日内の重複通報が 2件目で拒否されることを確認
